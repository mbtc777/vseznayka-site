Документы

Покажи все реквизиты документа «Возврат товаров от клиента» №ТДКА-000765 — что заполнено, что нет

Что делает агент. Читаю шапку через ОбщегоНазначения.ЗначенияРеквизитовОбъекта (список реквизитов беру из метаданных), затем перебираю все табличные части.

ИменаРеквизитов = Новый Массив;
Для Каждого Р Из Метаданные.Документы.ВозвратТоваровОтКлиента.Реквизиты Цикл
    ИменаРеквизитов.Добавить("" + Р.Имя);
КонецЦикла;
Значения = ОбщегоНазначения.ЗначенияРеквизитовОбъекта(Ссылка,
    СтрСоединить(ИменаРеквизитов, ","));
// печатаю только заполненные — так видно, что реально задано

Ответ. У документа заполнено 28 реквизитов из 60: Организация, Партнёр = Контрагент, Договор, Склад, Подразделение, Валюта, НалогообложениеНДС = «Продажа не облагается НДС», ХозяйственнаяОперация = «Возврат товаров от клиента», СпособКомпенсации = «Вернуть денежные средства», ПорядокРасчетов = «По расчетным документам», ОбъектРасчетов = сам документ. ТЧ: Товары — 1 строка (650 ₽, ставка «Без НДС»), Серии — 1, РасшифровкаПлатежа — 1. Автор, Руководитель, СуммаДокумента — служебные.

Какие поля этого документа обязательны к заполнению?

Что делает агент. Разбираю метаданные: у каждого реквизита смотрю свойство «Проверка заполнения» (FillChecking).

Для Каждого Р Из Метаданные.Документы.ВозвратТоваровОтКлиента.Реквизиты Цикл
    Если Р.ПроверкаЗаполнения = ПроверкаЗаполненияРеквизитаОбъектаМетаданных.ВыдаватьОшибку Тогда
        // выводим имя реквизита
    КонецЕсли;
КонецЦикла;

Ответ. Обязательные жёстко: Организация, Партнёр, Контрагент, Договор, Склад, Валюта, НалогообложениеНДС, ХозяйственнаяОперация, ВариантПриемкиТоваров, СпособКомпенсации. Плюс условные — только при определённой операции: КлиентКонтрагент/КлиентПартнёр/КлиентДоговор (комиссия), Номер/Дата расходного кассового ордера (если выданы деньги), ПодразделениеПроизводства (если есть производство).

Какого типа поле «Ставка НДС» в строках товаров?

Что делает агент. Смотрю тип реквизита табличной части в метаданных — это важно: от типа зависит, что можно присвоить кодом.

Тип = Метаданные.Документы.РеализацияТоваровУслуг.ТабличныеЧасти.Товары
    .Реквизиты.СтавкаНДС.Тип;
// -> СправочникСсылка.СтавкиНДС

Ответ. Это ссылка справочника «Ставки НДС», а не перечисление. В базе 17 значений: «Без НДС», 0 %, 5 %, 7 %, 10 %, 15,25 %, 16,67 %, 18 %, 20 %, 22 % и расчётные 10/110, 20/120, 22/122, 5/105, 7/107. Присвоение значения перечисления в такое поле не вызывает ошибки — но записывает пустую ссылку, и документ потом не проводится.

Сколько реквизитов и табличных частей у документа «Реализация товаров и услуг»?

Что делает агент. Читаю метаданные документа и перечисляю состав.

// 99 реквизитов, 10 табличных частей:
// Товары (38 колонок), СкидкиНаценки, ВидыЗапасов, ДополнительныеРеквизиты,
// РасшифровкаПлатежа, Серии, ЭтапыГрафикаОплаты, ШтрихкодыУпаковок,
// НачислениеБонусныхБаллов, СкладыСведенияДоставки

Ответ. 99 реквизитов шапки и 10 табличных частей. В ТЧ «Товары» 38 колонок, из них вручную заполняются около 15, остальные (ВидыЗапасов, АналитикаУчетаНоменклатуры, ИдентификаторСтроки, КодСтроки, КлючСвязи, СуммаНДСРегл/Упр) база пересчитывает при записи.

Проверь, что документ создастся с этими данными, но НЕ записывай в базу

Что делает агент. Создаю объект в памяти, заполняю шапку и строки, возвращаю объект без метода Записать. Ничего не попадает в базу.

Док = Документы.ПриобретениеТоваровУслуг.СоздатьДокумент();
Док.Дата = ТекущаяДата();
Док.ХозяйственнаяОперация = Перечисления.ХозяйственныеОперации.ЗакупкаУПоставщика;
Док.Организация = ...; Док.Договор = ...; Док.Склад = ...;
// строки ТЧ, проверка заполнения — и НИ ОДНОГО Док.Записать()

Ответ. Так проверяются любые сценарии без риска: заполнение проходит, ошибки типов и несуществующих полей видны сразу, а в базе ничего не меняется. Этим же приёмом проверены все 4 документа цепочки: приход → реализация → возврат от клиента → возврат поставщику.

Остатки товара на складе на конец месяца

Что делает агент. Запрос к регистру накопления с виртуальной таблицей остатков.

ВЫБРАТЬ
    Остатки.Номенклатура, Остатки.Склад,
    Остатки.КоличествоОстаток КАК Количество
ИЗ РегистрНакопления.ТоварыНаСкладах.Остатки(&Дата, Склад = &Склад) КАК Остатки
ГДЕ Остатки.КоличествоОстаток <> 0
УПОРЯДОЧИТЬ ПО Остатки.КоличествоОстаток

Ответ. Возвращает остаток в разрезе номенклатуры и склада на дату. Если нужно без движений — беру «ОстаткиИОбороты» и смотрю колонку «КонечныйОстаток».

Где сейчас находится конкретная серия товара — кто отгрузил, кому, по какому документу

Что делает агент. Ищу движения серии в регистре «Движения серий товаров» и вытаскиваю реквизиты регистратора.

ВЫБРАТЬ
    Д.Получатель, Д.Отправитель, Д.Регистратор,
    Д.Регистратор.Контрагент КАК Контрагент,
    Д.Регистратор.Договор КАК Договор,
    Д.Регистратор.Дата КАК ДатаОтгрузки,
    Д.Номенклатура
ИЗ РегистрНакопления.ДвиженияСерийТоваров КАК Д
ГДЕ Д.Серия = &Серия

Ответ. По серии видно всю цепочку: склад-получатель, отправитель, документ-регистратор, контрагент и договор. Если движений нет — серия ещё не отражена в базе, тогда сообщаю об этом прямо, а не подставляю пустые значения молча.

Не сходится себестоимость: покажи движения по регистратору

ВЫБРАТЬ Рег.Регистратор, Рег.Номенклатура, Рег.Склад,
    Рег.Стоимость КАК Стоимость, Рег.Количество КАК Количество
ИЗ РегистрНакопления.СтоимостьТоваров КАК Рег
ГДЕ Рег.Регистратор = &Документ

Ответ. Даёт построчный разбор: что именно списалось и по какой стоимости. Дальше сравниваю с партией прихода и показываю расхождение в конкретной строке, а не «в среднем по документу».

Сколько строк и на какую сумму реально легло в регистр за период

ВЫБРАТЬ НАЧАЛОПЕРИОДА(Р.Период, МЕСЯЦ) КАК Месяц,
    КОЛИЧЕСТВО(*) КАК Строк, СУММА(Р.СуммаУпр) КАК Сумма
ИЗ РегистрНакопления.ФактическиеДанныеБюджетирования КАК Р
ГДЕ Р.Период МЕЖДУ &Начало И &Конец
СГРУППИРОВАТЬ ПО НАЧАЛОПЕРИОДА(Р.Период, МЕСЯЦ)

Ответ. Пример из живой задачи: 1 149 строк и 73 519 907,81 ₽ за пять месяцев, по месяцам 17,8 / 17,0 / 13,4 / 12,8 / 12,5 млн ₽. Именно так нашлось, что суммы в регистре есть, а в отчёт не попадают.

Бюджеты и отчёты

В бюджетном отчёте пустая ячейка по статье ФОТ — где искать причину?

Что делает агент. Разбираю цепочку: правило получения факта → его схема → регистр факта → правила расчёта → механизм отчёта.

// 1) правило и его схема
Об = Справочники.ПравилаПолученияФактаПоСтатьямБюджетов.ПолучитьОбъект();
// 2) есть ли данные в регистре факта
ВЫБРАТЬ КОЛИЧЕСТВО(*) ИЗ РегистрНакопления.ФактическиеДанныеБюджетирования
// 3) есть ли правила расчёта по статье
ВЫБРАТЬ * ИЗ Справочник.ПравилаРасчетаСвязанныхОстатковИОборотовБюджетов

Ответ. Нашлось три уровня: правило считает правильно (1 149 строк, 73,5 млн ₽), но у суммы не было алиаса «СуммаВВалюте» — подсистема распознаёт только СуммаУпр / СуммаРегл / СуммаВВалюте. После правки схемы суммы появились, но отчёт всё равно пустой: регистр «Фактические данные бюджетирования» пуст по всей базе, а записей в «Правилах расчёта» по этой статье нет.

Какие имена полей понимает подсистема бюджетирования в схеме правила?

Что делает агент. Ищу в модуле «БюджетированиеСервер» процедуру, которая раскладывает поля схемы по суммам.

// БюджетированиеСервер.ЗаполнитьИсточникиСуммыПоСхеме
// распознаются ровно три имени:
//   СуммаУпр, СуммаРегл, СуммаВВалюте

Ответ. Только три: СуммаУпр, СуммаРегл и СуммаВВалюте. Поле с алиасом «Сумма» игнорируется, а «СуммаВФункциональнойВалюте» подсистема вычисляет сама из СуммаУпр. Поэтому отчёт, который читает СуммаВВалюте, показывал ноль.

Покажи обороты бюджета по статье за год

Что делает агент. Запрос к регистру «Обороты бюджетов» с группировкой по периодам.

ВЫБРАТЬ О.Период, О.Статья, О.Сценарий,
    О.СуммаОборот КАК Сумма
ИЗ РегистрНакопления.ОборотыБюджетов КАК О
ГДЕ О.Статья = &Статья И О.Период МЕЖДУ &Начало И &Конец

Ответ. Даёт план/бюджет по статье в разрезе сценариев. Важно: это обороты бюджета (план), а фактическая часть бюджетирования живёт в отдельном регистре — их нельзя мешать в одном запросе.

Почему отчёт показывает не то, что в регистре?

Что делает агент. Смотрю не данные, а код: какие поля отчёт реально читает и из чего строит запрос.

// БюджетнаяОтчетностьРасчетКэшаСервер:
//   если ХранимыеФактическиДанные -> регистр фактических данных
//   иначе если есть ПравилаРасчета -> запрос по правилам статьи
//   иначе -> ОборотыБюджетов (только план)

Ответ. Причина оказалась в третьей ветке: ни хранимого факта, ни правил расчёта по статье — отчёт молча берёт только план. Лечится либо включением промежуточного кэширования у правила (тогда факт пишется в регистр), либо формированием правила расчёта по статье.

Справочники

Найди номенклатуру по части названия

Что делает агент. Запрос с ПОДОБНО и выводом ссылки, артикула, единицы измерения.

ВЫБРАТЬ ПЕРВЫЕ 20 Н.Ссылка, Н.Наименование, Н.Артикул, Н.ЕдиницаИзмерения
ИЗ Справочник.Номенклатура КАК Н
ГДЕ Н.Наименование ПОДОБНО &Маска И НЕ Н.ПометкаУдаления

Ответ. Работает и для поиска по коду/артикулу. Если ничего не найдено — предлагаю уточнить: возможно, товар называется иначе или помечен на удаление (такие по умолчанию отфильтровываю).

Какой объект расчётов соответствует договору?

Что делает агент. В справочнике объектов расчётов ищу элемент по договору и типу расчётов.

ВЫБРАТЬ ПЕРВЫЕ 1 О.Ссылка
ИЗ Справочник.ОбъектыРасчетов КАК О
ГДЕ О.Договор = &Договор
  И НЕ О.Служебный
  И О.ТипРасчетов = &ТипРасчетов   // РасчетыСКлиентом / РасчетыСПоставщиком
УПОРЯДОЧИТЬ ПО О.Ссылка

Ответ. По одному договору в базе бывает 5 объектов расчётов — под разные типы (с клиентом, с поставщиком, с кредитором, с дебитором). Если взять первый попавшийся, документ запишется, но взаиморасчёты лягут не туда. Поэтому фильтрую по типу, а если по типу пусто — беру любой неслужебный.

Какие ставки НДС есть в базе?

Что делает агент. Перебираю справочник «Ставки НДС».

ВЫБРАТЬ С.Наименование, С.Ставка, С.ПредставлениеСтавки
ИЗ Справочник.СтавкиНДС КАК С УПОРЯДОЧИТЬ ПО С.Наименование

Ответ. 17 значений: Без НДС, 0 %, 5 %, 7 %, 10 %, 15,25 %, 16,67 %, 18 %, 20 %, 22 % и расчётные (10/110, 20/120, 22/122, 5/105, 7/107, 18/118). Отдельно напоминаю: это справочник, а не перечисление.

Есть ли серия с таким номером?

Что делает агент. Поиск по номеру и наименованию серии.

ВЫБРАТЬ ПЕРВЫЕ 5 С.Ссылка, С.Номер, С.Наименование, С.Номенклатура
ИЗ Справочник.СерииНоменклатуры КАК С
ГДЕ С.Номер = &Номер ИЛИ С.Наименование = &Номер

Ответ. Если серия не найдена — говорю об этом явно и не создаю её «на лету»: создание серий в базе меняет данные, для этого нужно отдельное разрешение.

Метаданные

Покажи структуру документа: реквизиты, типы, табличные части

Что делает агент. Прохожу по метаданным и собираю реквизиты с типами и признаком обязательности.

Для Каждого Р Из Метаданные.Документы.ПриобретениеТоваровУслуг.Реквизиты Цикл
    Имя = Р.Имя; Тип = Р.Тип; Обязательность = Р.ПроверкаЗаполнения;
КонецЦикла;
// 83 реквизита, ТЧ: Товары, ДополнительныеРеквизиты, РасшифровкаПлатежа,
// Серии, ВидыЗапасов, ЭтапыГрафикаОплаты, ШтрихкодыУпаковок

Ответ. Такая выгрузка — основа для генерации кода: видно имена, типы (справочник / перечисление / документ / число / булево) и что обязательно. На ней же построены карты реквизитов для всех четырёх документов цепочки.

Диагностика

Документ не проводится — с чего начать?

Что делает агент. Смотрю проверку заполнения, затем движения регистров, затем остатки.

// 1) ПроверитьЗаполнение / обязательные реквизиты
// 2) есть ли движения: ВЫБРАТЬ ИЗ РегистрНакопления... ГДЕ Регистратор = &Док
// 3) хватает ли остатков под списание

Ответ. Порядок всегда один: обязательные поля → движения → остатки → дата запрета изменений. Так отсекаются 90 % причин, и не приходится гадать.

Сумма в документе правильная, а в отчёте ноль

Что делает агент. Сравниваю, какое поле читает отчёт, с тем, что реально заполнено в документе.

// в документе: Сумма = 1000, СуммаСНДС = 1200
// в отчёте читается: СуммаВВалюте / СуммаВзаиморасчетов
// -> проверяем, заполнено ли именно это поле

Ответ. Классика: отчёт читает не то поле, которое заполнено. Аналогично в бюджетном отчёте: данные есть в СуммаУпр, а отчёт читает СуммаВВалюте.

Почему пусто в расшифровке ячейки отчёта?

Что делает агент. Иду по той же цепочке, что и отчёт: источник → отбор → агрегат.

// расшифровка строится из того же запроса, что и ячейка,
// но без группировки по статье
// -> если ячейка пуста, расшифровка пуста по той же причине

Ответ. Расшифровка не показывает «больше данных», она раскрывает тот же запрос. Поэтому её пустота подтверждает, что проблема в источнике, а не в свёртке.

Проверь, нет ли в моём коде типовых ошибок 1С

Что делает агент. Статическая проверка: имена реквизитов и перечислений сверяю с метаданными, смотрю опасные приёмы.

// Сверка: все Док.Х / Стр.Х / Перечисления.Х.Y существуют в метаданных
// Плюс список питфоллов: Об[Имя] у объекта, алиас «В» в запросе,
// СтрРазделить без разделителя, перечисление в поле-справочник

Ответ. Так отлавливаются ошибки, которые не видны при компиляции: например присвоение перечисления в поле-справочник (молча пустая ссылка) или обращение к реквизиту через оператор [] у объекта документа.
